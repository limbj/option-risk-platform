# 1단계 구현 계획과 경계

기준: 2026-11-08, `PROJECT_BRIEF.txt`의 Django 설계.

## 이번 단계

1. Python 3.12와 uv를 사용하고 Django 5.2 LTS 최신 패치 및 직접·간접 의존성을
   `uv.lock`으로 고정한다. Windows 개발 환경과 Linux 이미지에서 같은 잠금 파일을 사용한다.
2. Django/DRF 설정, 5개 앱 경계, 세션 인증·CSRF·기본 인증 권한과 생존 확인 경로를 만든다.
3. `quant`와 `ml`을 Django·DB 없이 import 가능한 패키지로 둔다.
4. 불변 금융 값 객체, 엄격한 입력 파서, 단위·날짜·부호·식별자 검증과 합성 예제를 만든다.
5. 금융 규칙 테스트와 Django 초기 구성 테스트를 분리하고 Ruff·pytest·Compose CI를 구성한다.

## 이번에 구체화한 결정

- **uv 0.13.7 / Python 3.12 전용 호환 범위**: 초기 검증 대상을 좁히고
  `uv sync --locked`로 재현한다. NumPy/SciPy/QuantLib/PyTorch는 실제 사용 단계에 추가한다.
- **USD / SYNTH_INDEX**: 단일 통화·합성 지수를 위한 데모 식별자이며 실제 시장 데이터가 아니다.
- **수량**: 0이 아닌 부호 있는 정수 계약 수, 별도의 LONG/SHORT과 일치해야 한다.
  계약 승수는 양의 유한 실수다. 소수 계약은 초기 범위에 포함하지 않는다.
- **만기/변동성**: 만기일은 평가일보다 엄격히 뒤여야 하며 sigma0 > 0을 요구한다.
  당일 만기/제로 변동성의 한계 가격은 후속 엔진에서 별도로 설계하기 전에는 받지 않는다.
- **단위**: 금리는 연속복리 연율 소수, sigma0는 연율 변동성 소수.
  외부 시나리오는 `spot_shock_pct`, `sigma0_shock_pp`, `rate_shock_bp`로 구분한다.
- **입력 상한**: 포지션/시나리오 각각 100개. 실제 계산 벤치마크 이후 조정한다.
- **테스트 DB**: 메모리 SQLite는 초기 Django smoke/session 테스트 전용이다.
  애플리케이션 설정은 PostgreSQL이며 4단계 영속성·트랜잭션 검증도 PostgreSQL에서 한다.
- **불변성의 범위**: 이번 값 객체는 frozen dataclass/tuple이다. 발행 스냅샷의 DB 불변성,
  해시·버전·계산 출처는 4단계에서 구현한다. 현재 코드가 이를 보장한다고 주장하지 않는다.
- **컨테이너**: 이번 Compose는 개발·호환성 확인용이다. Redis를 준비하지만 Celery 실행과
  durable outbox는 4단계다. 실제 배포 구성과 운영 보안 설정은 7단계다.

## 단계별 후속 순서

| 단계 | 산출물 | 주요 수용 기준 |
|---|---|---|
| 2 | Black–Scholes, 포지션 가치·완전한 합계, 스트레스 변환 | 독립 기준가격, put-call parity, 가격 경계, long/short·실패 합계 처리 |
| 3 | QuantLib Heston 어댑터, 기준 민감도 | 평가일 격리, 고정 모델 명세, bump/reprice 단위·수렴 검증 |
| 4 | 버전 입력·run/result ORM, DRF, outbox·Celery | 소유권, CSRF, 불변 스냅샷, 중복 처리·워커 손실·복구 검증 |
| 5 | React/TypeScript 4개 화면 | 입력부터 실행·부분 실패·이력·CSV/JSON까지 사용자 흐름 |
| 6 | MLP 학습·검증·COMPARE | 모델/데이터 해시, 외삽 거부, 영역별 오차·공정한 속도 비교 |
| 7 | 배포·재현 데모 | PostgreSQL/워커 복구·E2E·운영 문서 |

계산 실패를 0으로 바꾸지 않고, 필요한 모든 셀이 완료된 경우에만 합계/P&L을 제공한다는
원칙은 후속 가격·집계·영속성 구현에 적용한다. 이번 단계에는 가격과 집계 함수가 없다.
