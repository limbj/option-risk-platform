PROJECT GOAL

Build a portfolio project demonstrating financial mathematics, quantitative model validation,
ML, and reliable software engineering through an option position valuation and stress-testing system.
The intended workflow is: positions -> fixed market/model inputs -> valuation -> stress P&L -> reproducible reports.
Use a single repository with an API process and separate calculation worker sharing Python packages.

AGREED TECHNOLOGY STACK

- Python 3.12 as the initial compatibility target; verify dependency compatibility and lock versions during bootstrap.
- Django 5.2 LTS with its latest supported patch, Django REST Framework, Django ORM and migrations.
- Django session authentication with CSRF; ownership and per-resource authorization must be implemented explicitly.
- Django Admin for internal operations and inspection. Published snapshots, model artifacts, and completed results are immutable/read-only.
- React + TypeScript + Vite, TanStack Query, Plotly.js for the user interface.
- PostgreSQL for application data, immutable versions, run state, and results.
- Celery + Redis for background valuation jobs; use Linux containers through Docker Desktop/WSL2 on Windows.
- NumPy, SciPy, QuantLib for numerical work; PyTorch for the pricing surrogate.
- pytest-django, Hypothesis, Vitest, Playwright; Docker Compose and GitHub Actions.
- Django replaces the earlier FastAPI proposal. Use Django ORM/migrations rather than adding SQLAlchemy/Alembic.

SUGGESTED CODE BOUNDARIES

- Django apps: accounts, portfolios, marketdata, valuations, model_registry.
- quant package: Black-Scholes, Heston adapter, sensitivities, stress transformations, portfolio aggregation.
- ml package: dataset generation, training, validation, inference, artifact manifests.
- DRF views handle HTTP validation and call application use cases. Celery tasks orchestrate the same use cases.
- Keep quant/ml code usable without Django or a database. Avoid heavy calculations inside HTTP views or database transactions.

INITIAL FINANCIAL SCOPE

- One synthetic, non-dividend-paying underlying index and one currency.
- European cash-settled calls and puts; flat interest rate and q = 0 initially.
- ACT/365F as the initial time convention. Validate eligible maturities against the valuation date.
- Long quantities positive, short quantities negative; quantities and positive contract multipliers are explicit.
- Position value = signed quantity * multiplier * per-unit option price.
- Stress P&L = stressed value - base value. Compare like-for-like models/engines and retain both inputs.
- Implement Black-Scholes directly and cross-check it. Use QuantLib AnalyticHestonEngine as the Heston reference engine.
- Compute base Delta, Gamma, and initial-volatility sensitivity with clearly documented units and bump/reprice settings.
- The initial Heston profile fixes kappa, theta, vol-of-vol xi, and correlation rho. These values belong to the versioned model specification.
- Market snapshots supply spot, r, and initial variance v0 (or initial volatility sigma0 = sqrt(v0)).
- Heston volatility stress means an absolute change in sigma0: v0_new = (sqrt(v0) + delta_sigma0)^2.
  Example: +5 volatility percentage points means delta_sigma0 = 0.05, not a 5% relative increase.
  Keep other Heston parameters fixed; reject financially invalid shocks instead of silently clamping them.
- Label this risk measure "initial-volatility sensitivity" rather than implying an unspecified market-IV Vega.
- Rate shocks use explicit basis points: +100 bp = +0.01. Spot shocks are relative percentages.
- Initial stresses are instantaneous: hold the valuation date and residual maturity fixed.
- Pricing is risk-neutral model valuation. Deterministic stress results are not VaR/ES or probability forecasts.
- Use synthetic fixtures and manual/CSV inputs initially. No live market feed is required to complete the MVP.

ML INCLUDED IN THE FIRST COMPLETE MVP

- Train one small MLP pricing surrogate offline.
- Initial inputs: log(S/K), residual maturity T, flat rate r, and initial volatility sigma0.
- Output: normalized call price C/K; derive puts using put-call parity under the same assumptions.
- Heston kappa/theta/xi/rho and q are fixed by the artifact's model specification. A different specification requires a compatible artifact/version.
- Generate teacher labels using the Heston reference engine. Heston European pricing has a semi-analytic method;
  benchmark against that method rather than claiming speed gains only against a slow Monte Carlo implementation.
- Provide REFERENCE and COMPARE execution modes. Authoritative valuations and base sensitivities initially use the reference engine.
- COMPARE evaluates the same positions and scenarios with the reference engine and ML, showing price/P&L errors and timings.
- For unsupported ML inputs, record the reason and retain reference results; do not fabricate ML results or mix base/stress engine values silently.
- Initial production risk sensitivities use the reference engine. Any NN-derived sensitivity needs its own validation before use.
- Validate average, maximum and percentile price errors; near-expiry/ITM/OTM/stress-boundary errors; portfolio stress P&L errors;
  pricing bounds and parity; and runtime at equal workloads and accuracy targets.
- Include held-out parameter regions and out-of-domain cases in addition to random splits.
- Record preprocessing, feature order, training domain, dataset hash, seed, software versions, dtype/device, artifact hashes, and numerical settings.
- Compare warmed inference and an appropriately reused reference engine; report core computation and end-to-end API timings separately.
- Set explicit error/performance gates after measuring the baseline. No speedup or accuracy result has yet been established.

EXECUTION AND DATA ARCHITECTURE

- Principal records: PortfolioVersion, MarketSnapshot, ScenarioSetVersion, ModelVersion, ValuationRun,
  ValuationResult, RunChunk, OutboxEvent. Exact schema remains to be designed in the new conversation.
- A run pins input/version IDs and hashes, valuation date, numerical/model settings, code version, and artifact version.
- POSTing a run returns HTTP 202 with a durable run ID. UI polling is sufficient for initial progress updates.
- Create the run and outbox event in one Django transaction.atomic() block. A dispatcher publishes pending messages to Redis.
- transaction.on_commit() may wake the dispatcher, but is not a substitute for durable outbox/recovery.
- Queue messages carry IDs rather than large mutable objects. Workers reload only pinned versions.
- Make processing idempotent through result uniqueness, chunk state, execution/attempt tokens, and expired-work recovery.
- Record completed and failed cells separately. A scenario total is available only when all required position results are complete.
  Stress P&L also requires complete base and stressed valuations. Do not substitute zero for failures.
- QuantLib evaluation-date state must be isolated appropriately. Begin with process-based workers and an explicit evaluation date per task.
- Retain calculation provenance and model/source labels in reports. Compare reruns within declared numerical tolerances.
- Initial input cap proposal: 100 positions * 100 scenarios, adjusted using actual measurements.

MVP USER FEATURES

1. Positions: manual entry/CSV import, explicit side/quantity/multiplier, immutable portfolio versions.
2. Market data: sample/manual snapshots with validation and fixed valuation dates.
3. Valuation: per-position value and complete portfolio totals; base sensitivities.
4. Stress tests: presets and custom spot/initial-volatility/rate shocks; P&L tables and heatmaps.
5. Run management: queued/running/completed/failed or partial-error states, progress, failure reasons, retry and history.
6. ML validation: supported-domain display, reference/ML comparison, errors and timing reports.
7. Export: CSV/JSON including calculation assumptions, input/version identifiers, and completeness status.

Four primary screens: positions; market/scenario configuration; valuation results/history; ML validation.
